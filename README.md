# build-team-standards

Claude Code plugin marketplace for SMB Strategy Consultants' external build teams (Spot2Bee and whatever comes after it). One plugin today: **`engineering-standards`**.

## What this is, and why it's a separate marketplace

The engineering-standards package for build teams originally shipped as a static zip (`builder-team-core.zip`, distributed via a Google Drive folder) — `CLAUDE.md` + skills + docs, unzipped into the workspace root above each cloned repo. That still works and still ships that way for the parts that are pure workspace-root overlay (`CLAUDE.md`, `ENGINEERING-CORE.md`, `ENGINEERING-WORKSPACE.md`, `REVIEW.md`, `WORK-LOG-PROTOCOL.md`, `CONTEXT-WINDOW-CONTROL.md`, `CLOUD-SAFETY-PROTOCOL.md`, `documentation-templates/`).

What the zip **cannot** carry is enforcement — hooks. `REVIEW.md` and `CONTEXT-WINDOW-CONTROL.md` were advisory prose only: nothing stopped a session from ending with unreviewed code, and nothing nagged before the context window filled. This marketplace exists to ship that enforcement, auto-updating, without asking every build-team member to manually re-download and re-unzip a file every time a hook changes.

It is **not** part of `smb-skills-marketplace` (the other SMB Strategy Consultants marketplace) on purpose: that marketplace's own README explicitly forbids hooks, because it also serves Claude chat/Desktop/Cowork, where hooks silently do nothing. This one is Code-only, and says so.

## Installing

Run these from your workspace root — `--scope project` scopes to whatever directory the command runs in, not to "the workspace" abstractly. Running it from your home directory (or any other cwd) installs it there instead, applying its hooks to every project on the machine, not just this one. Check with `pwd` first if unsure:

```
cd /path/to/your/workspace-root
claude plugin marketplace add SMBStrategyConsultants/SMB-Plugin-Builders
claude plugin install engineering-standards@build-team-standards --scope project
```

A hand-written `extraKnownMarketplaces`/`enabledPlugins` block in `.claude/settings.json` alone is **not** enough — it registers the marketplace but does not fetch an external-source plugin, so the hooks never actually load, with no error surfaced. Verified against real Claude Code behavior, not assumed. Restart Claude Code after installing (`/clear` doesn't reload plugin config — it only resets the conversation).

Mis-scoped it already (ran from the wrong directory)? Uninstall and reinstall from the right one:
```
claude plugin uninstall engineering-standards@build-team-standards
cd /path/to/your/workspace-root
claude plugin install engineering-standards@build-team-standards --scope project
```

**Add `.agent/tmp/` to your project's own `.gitignore`.** The review-gate and context-nag hooks write session state (an audit log of review clears/waivers, per-session edit tracking) to `<your project>/.agent/tmp/code-review/` — inside the repo you're building, not inside this plugin. Without an ignore rule, `git add -A` picks it up and reviewer verdict text/waiver reasons end up committed.

## What `engineering-standards` ships

- **Skills** (12 dirs, mirrored from `builder-team-core/skills/`): karpathy-coding, clean-code, code-review, code-review-checklist, testing-patterns, tdd-workflow, systematic-debugging, python-patterns, nodejs-best-practices, database-design, api-patterns, architecture.
- **Hooks**:
  - `code-edit-tracker.sh` + `code-review-gate.sh` (paired) — turns `REVIEW.md`/`ENGINEERING-CORE.md §17`'s review protocol into an enforced Stop-hook gate. Ending a turn with unreviewed code blocks until the gate is cleared (reviewed, waived with a reason, or risk explicitly accepted) — every clear is durably logged.
  - `code-review-reminder.sh` — fires on a review-shaped prompt, restates the §17.9 contract (fresh agent, minimal unbiased brief, edited-file anchor set).
  - `secret-read-guard.sh` — denies shell commands that would print secret *values* (not names) to the transcript.
  - `destructive-command-guard.sh` — forces a two-stage confirmation gate (`CLOUD-SAFETY-PROTOCOL.md` §0) before a destructive AWS/GCP/Azure/Terraform/k8s/database command runs. Fires on the actual invocation, not on mentioning the tool.
  - `work-log-reminder.sh` — non-blocking Stop-hook nag: if code changed this session but `WORK-LOG.md` wasn't touched, says so before the session ends.
  - `slack-post-tracker.sh` + `slack-post-reminder.sh` (paired, v1.5.0) — same shape as `code-edit-tracker.sh`/`work-log-reminder.sh`: tracks whether `gh pr create` ran this session and whether any Slack MCP tool call ran; if a PR opened and Slack stayed silent, nags at Stop — repeats each Stop until a Slack call happens, same re-fire behavior as `work-log-reminder.sh` below, not a one-shot. Non-blocking — see Known limitations below for what it can't detect.
  - `context-gate.py` — nags before the harness auto-compacts, so open state gets noted first. Same mechanism as `CONTEXT-WINDOW-CONTROL.md` describes, now enforced instead of just documented.
- **Documentation templates**, mirrored from `builder-team-core/documentation-templates/`.

## Versioning

Bump `plugins/engineering-standards/.claude-plugin/plugin.json`'s `version` (and the matching entry in `.claude-plugin/marketplace.json`) on any change to what ships. Installed clients pick up the new version on their next plugin sync.

## Known limitations (logged, not silently skipped)

From FULL + security review of `destructive-command-guard.sh` / `work-log-reminder.sh` (v1.1.0). All LEDGER-disposition — real, not blocking, tracked here so they don't get rediscovered as if new:

- **`destructive-command-guard.sh` register has coverage gaps**: `aws s3 sync --delete`, unqualified `DELETE FROM`/`UPDATE ... SET` without a `WHERE`, `terraform state rm`, `kubectl scale --replicas=0`, `aws ecr batch-delete-image`, `aws elbv2 delete-*`. Fix the doc first (`CLOUD-SAFETY-PROTOCOL.md` §2 in `builder-team-core`), then the register, so they stay in sync.
- **The gate is enforced by the model reading `additionalContext`, not by the hook itself.** `permissionDecision: "ask"` produces one permission prompt; a single "yes" runs the command with zero confirmation stages completed unless the agent honors the injected two-stage instructions. The hook does not read `permission_mode`, so behavior under `bypassPermissions`/`auto` modes is unverified. A person reading the prompt is the actual control here.
- **`bash -c "aws …"` and `bash <<<"aws …"` are known, deliberate gaps** in Gate 1's command-position detection — closing either needs a quote character in the separator class, which reopens the exact false positive (`grep -rn 'kubectl delete' docs/`) position-anchoring was built to fix.
- **A wrapper word followed by its own flag isn't covered** — `xargs -0 kubectl …`, `env -i aws …`, `timeout 60 terraform …`, `nice -n 10 terraform …` all bypass Gate 1; only the flagless form of each wrapper is recognized. The idiomatic form of most of these (`xargs -0`, `env -i`) is the one that bypasses. Needs a bounded flag-eater between wrapper and binary, deliberately not added in the same round as the wrapper-word fix itself to avoid stacking two unverified regex changes.
- **The heredoc-consumer detection (S-3 fix) can still be fooled by a terminator name that happens to spell a consumer word** — `cat <<SH >> notes.md` gates on the terminator `SH` matching `sh`, even though `cat` (not `sh`) consumes the heredoc. (The sibling case — a *redirect-target filename* spelling a consumer word, e.g. `cat <<EOF >> kubectl-notes.md` — is fixed: the opener line's `>`/`>>` redirect and its target are stripped before the consumer-word check.) The terminator-name case needs a boundary-tightening decision that risks breaking `/bin/bash <<EOF`, so it's logged rather than patched blind.
- **`grep`'s ERE complexity/length limits are the load-bearing control on the register pattern, not any code in this hook.** `$PATTERN` is ~1.8KB with 36 bounded-repetition groups; BSD grep (macOS) and GNU grep both accept it today, but this hook explicitly ships to "every project a build team works on" (varying OS/toolchains), and a `grep` implementation that rejects the pattern (rc=2) is handled identically to "no match" (rc=1) — silently disarming the guard. No fix applied; recorded as an environment dependency worth knowing about, not a code defect this hook can close.
- **`strip-heredocs.awk`'s two-pass terminator-existence check can still be fooled by a coincidental token recurrence** — text containing literal `<< EOF` inside a quoted string (not a real heredoc), followed later in the same command by an unrelated line that happens to read exactly `EOF` (e.g. a real heredoc's own terminator, further down), gets misread as one long fake heredoc spanning both — dropping everything in between from Gate 1's input. A strict improvement over the one-pass version (8/20 known failures → 3/20 on the same probe suite), not a regression, and closing it fully needs shell-quote-aware parsing that a line-based awk script can't cheaply do. Documented rather than patched further, to avoid a fourth regression cycle in this file this session.
- **`secret-read-guard.sh`'s continuation-join (shared awk mechanism) has the same environment dependency as `destructive-command-guard.sh`'s**: with `awk` genuinely absent, a backslash-continued secret-reading command can be missed (false negative) rather than denied. Same class as the grep-ERE-limits entry above.

**Process note on how these were found**: `destructive-command-guard.sh`/`strip-heredocs.awk` went through FULL → DELTA → DELTA → THIRD review this session (v1.1.0), each round finding real issues in the prior round's fix before converging. The THIRD-round reviewer's SIGPIPE-under-`pipefail` verification of the named trigger (a `grep -q` pipe exiting early on a match, causing the killed upstream `printf` to flip the pipeline's reported status to non-zero under `pipefail`, silently disarming an "ask" gate) surfaced the identical bug, unprompted, in the sibling `secret-read-guard.sh` — there flipping a `deny` into a silent allow on secret-value exposure, which is worse. Fixed the same way (herestring instead of pipe, at all 16 `grep -q` call sites) and re-verified directly against the reviewer's own methodology (padding sizes 32KB/64KB/74KB/111KB) rather than spawning a fourth review round for a single mechanically-identical, already-proven-safe transform — a proportionality call, logged here rather than left silent.
- **`work-log-reminder.sh`'s `worklogged.$sid` marker is forgeable** by writing to any path ending `WORK-LOG.md`, anywhere. Bounded impact — it only suppresses an advisory nag that structurally cannot block Stop (`systemMessage` only, no `decision` field).
- **`work-log-reminder.sh` re-fires on every Stop event**, not once — there's no dedup marker, so it repeats across the 3-5 Stop events a single blocked review-gate cycle typically triggers. Advisory-only, so the cost is repetition, not a wrong state.
- **Work-log detection is tool-shaped**: `code-edit-tracker.sh` only sets `worklogged.$sid` on a `Write`/`Edit`/`MultiEdit`/`NotebookEdit` touching `WORK-LOG.md`. An entry appended via `cat >> WORK-LOG.md <<EOF` from Bash doesn't set the marker, so a compliant agent can still get nagged. Noise, not a wrong state.
- **`slack-post-tracker.sh`'s `gh pr create` detection is a plain regex on the Bash command string, verified rather than assumed across two review rounds (FULL + DELTA, 2026-09-02 — see `.agent/REVIEW_LEDGER.md` SPR-01/02/03).** `bash -c "gh pr create ..."` genuinely evades it (verified, both rounds). `xargs`, `env -i`, `timeout` wrapping, command substitution/grouping (`` $(gh pr create ...) ``, backticks, parens), a WORK-LOG.md mention of the phrase (correctly does NOT mark, via `strip-heredocs.awk`), AND an executed heredoc (`bash <<EOF` / `gh pr create` / `EOF`, correctly DOES mark, via a ported heredoc-opener consumer check from `destructive-command-guard.sh`) all behave correctly — the DELTA round's first pass at the heredoc case shipped a real regression here (documented as an "accepted trade-off" that turned out to have a 6-line fix already sitting in the sibling hook) before the port closed it for real. What the matcher still cannot do, because it is line-based text matching and not a shell parser: distinguish a real invocation from a plain mention of the phrase in prose (`echo "remember to gh pr create later"` — same limitation class as `destructive-command-guard.sh`'s position-anchoring gaps, accepted since the false-positive direction is the safe one for `propened`), or distinguish a real `-h`/`--help` flag from that exact substring inside a quoted argument on the same invocation (`gh pr create --title "Add -h flag support"` will not mark — the `--help` exclusion is scoped per-invocation, not per-line, so it no longer vetoes a sibling real invocation on the same command line, but a quoted "-h" within the same invocation's own arguments still reads as the flag).
- **The pair can only detect a coarse proxy, not the actual SLACK-PROTOCOL.md triggers.** It knows "a PR opened this session" and "Slack was touched this session" — it cannot tell whether a blocker actually occurred, whether merge-ready actually applies, or whether the post that did happen used the right tag. A session that opens a PR with genuinely nothing post-worthy yet (no blocker, no milestone) still trips the reminder; that's why it's advisory, same as `work-log-reminder.sh`, never a gate.
- **`slackposted.$sid` is set by tool-name pattern-match on the *service*, not the verb** (any tool name containing `slack`, excluding anything containing `draft` or a read-only lookup verb — list/get/history/search/channels/users/info) — deliberately broad after the FULL review found the earlier verb-specific pattern (`*slack*send_message*`/`*slack*schedule_message*`) missed real tool names from Slack MCP servers other than the one it was written against (`slack_post_message`, `chat_postMessage`, `conversations_add_message` all went undetected, producing a permanent false nag on a contractor who DID post). The read-only exclusion was added after the DELTA round found the broadened match went too far the other way — `slack_list_channels`/`slack_get_channel_history` (the natural first step of finding `#build-<project>`'s ID before posting to it) also marked "posted," silently defeating the nag on exactly the session it exists to catch. Relies on the harness's `mcp__<server>__<tool>` naming and the server being named with "slack" in it — a Slack tool exposed under a differently-named server (`mcp__team-chat__chat_postMessage`) will not match; no tool inventory is pinned anywhere in this repo to match against instead. Also not confirmed against the message actually reaching the channel — a call that errors after the tool fires still marks the session as "posted." Same class of gap as `work-log-reminder.sh`'s forgeable marker — bounded impact, since this only suppresses an advisory nag.
